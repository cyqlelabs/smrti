```bash

pip install -e .

# Run all tests
pytest tests/

pytest tests/test_atomspace.py -v

pytest tests/test_retrieval.py::test_remember_and_recall -s

# CLI
smrti init --db ~/.smrti/memory.db --personality balanced --tenant-id default --space default
smrti status
smrti serve mcp        # MCP stdio server
smrti serve rest       # FastAPI on :8420

# Benchmark harnesses (need the datasets and an answering model; not CI gates)

make bench-baseline    # re-record the LongMemEval-S baseline
# DATASET and HALUMEM override the paths under data/; BENCH_ARGS passes flags through
```

## Architecture

Smrti is an AtomSpace-inspired memory engine for AI agents. It stores beliefs as graph nodes with Bayesian truth values, emotional valence, and attention weights in a single SQLite file with vector indexing (sqlite-vec).

**Entry point:** `src/smrti/__init__.py` — `Smrti` class is the public facade (`remember`, `recall`, `believe`, `reinforce`, `reflect`, `forget`, `status`).

**Core layers (`core/`):**
- `models.py` — Pydantic data structures: `Atom`, `TruthValue`, `AttentionValue`, `Valence`, `Evidence`, `RecallResult`. `Valence` carries two pairs: `valence`/`intensity` is the current mood that epoch propagation drags toward the atom's neighbours, and `intrinsic_valence`/`intrinsic_intensity` is the tone the atom was written with, which propagation never touches. Everything that judges a memory — severity, the salience valence term, the recall confidence bypass, the prune guard — reads the intrinsic pair via the `own`/`own_intensity` properties; only propagation reads the drifting one, and the drifting one is what a recall result reports as `valence`, for callers that want the mood a memory has absorbed (smrti-town's citizens decide where to go on it). Both intrinsic columns are nullable and are not backfilled, so an atom written before the split reads as its current values; every creation path now goes through `AtomSpace.add_atom`, so no new atom is written without them. `intensity` is a dimension the caller may state (`remember`/`believe`/MCP/REST take `intensity`); left unset it is `|valence|`, which is all the engine can read from a bare number. `PERMANENT_PROBABILITY` (0.95) is the threshold at or above which an asserted belief is born certain and exempt from confidence decay. `INITIAL_CONFIDENCE` is the confidence each kind of atom is born with, one value per kind whatever path created it (episode/concept/goal/relation 0.5, belief 0.3): an extracted concept used to start at 0.6 while the belief the user stated started at 0.3, and confidence is a fifth or more of the salience score on every preset. For episodes and concepts, which hold no proposition, confidence is retention strength and gates surfacing rather than truth. `SUPERSEDED_PROBABILITY` (0.1) is what a claim replaced by a later one is held at, under the 0.3 antipattern line. `Evidence` carries `text` (what was observed: the reason given to `believe`, what a supersession replaced) and `source` (who reported it)
- `atomspace.py` — Graph operations: add/update atoms, link atoms, boost STI, file and list evidence. `add_atom` is the one door every atom comes through (the facade, the entity resolver, healing, association discovery, bridging), so the columns every row needs — the intrinsic valence pair above all — are written on every row; it takes an optional precomputed `embedding` (the resolver already embedded the name to probe the index) and `require_vector=False` for a background writer whose encoder just failed, which stores the row without a vector rather than lose the atom. It raises `ValueError` when an existing atom ID is re-added under a different `(tenant_id, space)` — `INSERT OR REPLACE` keys on the primary key alone, so without the guard the row and its vector silently relocate into the other partition. `link_atoms` takes optional `metadata` (the supersession writer names the loser on a `contradicts` edge with it). `boost_sti` takes optional `tenant_id`/`space` arguments that make the write a no-op outside that partition
- `db.py` — SQLite schema (WAL mode). Tables: `atoms`, `vec_atoms` (virtual vec0 for KNN), `atoms_fts` (virtual fts5 for BM25, `unicode61 remove_diacritics 2`), `evidence` (append-only observation log), `personality`, `aliases`. `atoms_fts` is maintained by hand alongside `vec_atoms` rather than by triggers — `INSERT OR REPLACE` does not fire delete triggers unless recursive triggers are on, so a trigger-maintained index would accumulate a second row per rewritten atom. Both index tables are keyed on `stable_rowid(atom_id)`, 56 bits of SHA-256, because neither can be searched by `atom_id`: FTS5 has no secondary index, and a vec0 table answers `WHERE atom_id = ?` with a scan of every vector in the database — 86ms at twenty thousand atoms, on a query `add_atom` ran on every write, so write cost grew with the size of the whole graph. `fts_write`/`fts_delete` and `vec_insert`/`vec_delete` return the statements every write path appends to its batch, and `_vec_rowids_are_stable` triggers a one-time rebuild for a graph written before the keying. `_init_atoms_fts` rebuilds the index whenever it holds fewer atoms than the graph does, which repairs a database a build without this code has written to. A build with no FTS5 sets `Database.fts_enabled = False` and retrieval runs on vectors alone. Key methods: `execute_many` (batched executemany), `execute_batch` (multi-statement single transaction with rollback on failure), `close_database` / `clear_registry` (evict one or all entries from the shared registry — intended for test teardown). Schema additions are migrations that run on open (`_migrate_*`), each behind a file-level backup; `_migrate_evidence_columns` adds `text` and `source` to the evidence log of an older database. Data repairs run on open too (`_repair_legacy_rows`), behind the same backup whenever a row will change, and there is no repair registry because each is idempotent — it touches only rows that still carry the legacy shape, so it is safe every open and also mends what a process on older code writes later: an extracted entity with NULL intrinsic tone (resolver-made, so `content IS NULL`) gets it rebuilt from its incoming claim edges (the lowest claim valence under −0.3, else 0, which is what `_lower_tone` writes today; pre-split episodes are left alone since nothing records their tone); `associated` edges out of a person atom at confidence ≤ 0.2 — the old healing step's placeholders — are deleted; atoms stamped `$.forgotten` but still at or above the surfacing floor — the old `forget()` left them there — are sunk to half of it. The other data repair, lifting a drowned permanent belief, lives in the epoch and is kept from undoing a deliberate `forget()` by the stamp rather than by a record of having run
- `embed.py` — Thread-safe FastEmbed singleton (paraphrase-multilingual-MiniLM-L12-v2, 384 dims, ONNX CPU, 50+ languages)
- `provenance.py` — Atom authorship (`user` vs `agent`) stored in `metadata.$.source`; atoms with no recorded source read as user-authored. Exposes the `ATOM_SOURCE` SQL expression (CASE-guarded `json_extract` so malformed metadata never aborts a whole-table pass), the `VALENCE_STATED` metadata key (set when the caller stated the valence instead of letting it be estimated), and the `ATOM_OWN_VALENCE` / `ATOM_OWN_INTENSITY` expressions (`COALESCE(intrinsic_*, *)`) that read an atom's own tone back from SQL. Epochs use it to decay agent-authored atoms faster (multiplier `2.0 − agent_source_trust`), give them a lower LTI floor, and allow pruning agent-authored episodes/beliefs while user-authored ones are kept. The MCP `remember` tool accepts a `source` argument; the proxy tags assistant-turn episodes as `agent`

**Retrieval (`retrieval/`):** `fan_out.py` does (KNN ⊕ BM25) → 1-hop graph expansion → salience scoring → diversity cap. The two searches are fused by Reciprocal Rank Fusion (`_rrf_fuse`, k=60, ties broken on atom id so the same query always yields the same pool): vector distance and BM25 share no scale, and rank fusion needs none. The lexical half exists because embedding distance answers "is this about the same thing" and not "does this text contain this word" — a belief stored in one language scores well below a same-language pair against the query asking for it, while the proper nouns both hold are byte-identical. `_lexical_entry_points` quotes every query term so FTS5 syntax in a query (`NEAR`, `OR`, `*`) is searched for rather than obeyed, caps terms at 32, and returns nothing when the build has no FTS5. Only its top `_FTS_POOL` (10) hits reach the fusion: the head carries the proper nouns the embedding missed, the tail is every atom sharing a stop-word with the query, and fusing that tail evicted dense candidates holding the answers — five points of LongMemEval-S hit rate, while the ten-candidate head cost nothing. `text.py` holds the one tokenizer both the echo test and the diversity cap use. `diversify.py` runs after ranking: an episode that repeats one already selected from the same 10-minute window (word-set containment ≥ 0.7) yields its slot once that moment has spent its allowance of `max(2, top_k // 6)` repeats, and up to two slots are reserved for beliefs clearing `min_confidence_to_surface`. The allowance grows with the answer because the cost of a duplicate shrinks with it — a fifth of a five-slot reply, two percent of a fifty-slot one — and a flat cap of two was evicting real evidence at fifty slots, 2.5 points of hit rate. Both halves of "same moment" are load-bearing — a cap keyed on time alone cost the LongMemEval-S harness 30 points of retrieval hit rate, because a whole stored session shares one timestamp and capping the window capped the session. Skipped atoms are not dropped; they fill any slot left over, so a single-topic graph still returns a full top_k. The KNN entry pool scales with the space (`4·√N`, clamped to 50–256) so froth cannot crowd the gate on a large graph; the 1-hop expansion is capped at 100 edges per direction, ordered by `sti + lti + confidence` on the far endpoint so a hub of trivia cannot evict the one useful edge; expanded candidates are scored on their real stored embedding rather than similarity 0. Nothing else enters the candidate set: an earlier version added the three highest-standing person atoms to every query "to anchor the graph", and scored on their true similarity they carried none for most queries while their standing put them first — a person concept at similarity zero was the top result for a question about Kubernetes. An episode whose word overlap with the query is ≥80% of the *larger* of the two word sets (`text.coverage`, and only above 0.5 similarity) is a restatement of the question, not an answer, so its similarity term is zeroed and, since relevance gates standing, it scores nothing — beliefs and concepts are exempt, since searching for a fact by stating it must return the fact. Coverage rather than smaller-side containment because the verdict is final: an answer that contains every word of a three-word query is not a copy of it. A candidate whose salience is zero is not returned at all; the KNN probe returns its nearest neighbours however far they are. The `agent_source_trust` discount scales an agent-authored atom's standing terms — STI, confidence, LTI, valence — and spares similarity. Standing is what the graph has come to trust about an atom, and shrinking an agent's share of it is the discount's job; similarity says how much the atom is *about the question*, which is a property of the query. Discounting that too buried the one memory holding the answer whenever it was the agent's own reply, and the whole LongMemEval-S single-session-assistant category retrieved at zero. `salience.py` formula: `sim × (w_sim + w_sti×sti + w_conf×conf + w_lti×lti + w_val×|valence|×intensity)` — relevance multiplies standing rather than adding to it, so an atom that is not about the question cannot be salient to it however important it is elsewhere, and among atoms that are, standing decides the order. When valence < -0.5, weight dynamically shifts from `w_sti` to `w_valence` so old-but-critical errors outrank recent trivia. `retrieve()` takes `min_confidence=None` to mean the write space's `min_confidence_to_surface` — the floor a preset promises is the floor a caller gets — and `boost=False` to read without raising the attention of what came back; atoms stamped `$.forgotten` are never candidates. `classify.py` classifies recall results into severity levels (`critical_warning`, `known_antipattern`, `context`). A `critical_warning` requires all four of: the caller stated the valence (`VALENCE_STATED`), the atom is not a `concept`, own valence < -0.5, and own intensity > 0.5. Estimated valence scores the mood of the words — ordinary frustration in stored conversation is a speaker's tone, not a report of a mistake — and a bare concept label carries nothing to avoid doing again, so neither can mint a behavioural constraint. A `known_antipattern` is a belief at probability < 0.3 with confidence > 0.3, which is where a superseded preference or constraint lands.

**Evolution (`evolution/`):** `truth.py` holds the one revision rule: confidence is an evidence count (`c = n/(n+1)`), an observation adds `weight × lr` to the count, and the strength moves to the count-weighted mean — the PLN revision rule with `k = 1`, the same arithmetic `TruthValue.merge` does for two whole truth values. The epoch's evidence pass, reinforcement and bridge merging all use it, so confidence means the same thing wherever it is read. `reinforcement.py` accepts "this memory was used" as evidence — `reinforce_atoms` applies `update_truth` with a small weight and the atom's own probability as the observation, so probability holds still and only confidence moves. Guards: the atom must live in the write space, an atom stamped `forgotten` is never lifted, agent-authored atoms take the `agent_source_trust` discount, and `$.reinforced_epoch`/`$.reinforced_count` cap each atom at `CAP_PER_EPOCH` (3) reports per consolidation so a memory recalled every turn cannot ratchet on conversation volume. `epoch.py` runs consolidation cycles: process evidence log → decay STI, LTI, and confidence → propagate STI and valence to 1-hop neighbors → heal orphaned episodes → promote high-STI nodes to LTI → resolve contradictions → discover associations (every 10th epoch) → prune low-salience atoms. A `contradicts` edge that names a loser in `$.loser` (the supersession writer does) has that endpoint cut to `SUPERSEDED_PROBABILITY` and ×0.8 confidence; one that names none weakens the less confident endpoint's confidence only. An atom stamped `$.forgotten` holds no LTI floor and is pruned like agent output once its confidence is under the surfacing floor, user-authored or not. The epoch never grows bridge spaces: an earlier version compared the space against every other space in the tenant every tenth epoch and wrote `a_x_b` atoms wherever the overlap cleared a threshold nobody had set, a quadratic scan on a timer; bridging is the explicit `space_merge` call. `connections.py` is association discovery: for the top 50 atoms by LTI it searches for semantically similar atoms in the same space that are not already linked and creates a weak `associated` relation (confidence 0.1) for each pair within cosine distance 0.4 — paraphrase linking, named for what it does. `attention.py` handles STI propagation to neighbors. `valence.py` handles emotional valence propagation using a `mood_inertia`-controlled blend (existing valence × inertia + incoming signal × (1 − inertia)); high-inertia presets (e.g. `balanced`=0.8) drift slowly, low-inertia presets (e.g. `empathetic`=0.4) react faster. What it moves is the mood pair that recall results report as `valence`, which callers read (smrti-town's citizens avoid a place their memories have soured on); the engine's own judgements never do. `healing.py` detects orphaned episodes (episodes that mention concepts but no person atom) and links each to a person: the sole person when the space has one, otherwise the one person whose label or non-pronoun alias appears in the episode's text, and nobody when none or several do. It draws that one edge and no others — the placeholder person → concept edges an earlier version added made the person a hub joined to everything in the space.

**Extraction (`extraction/`):** `aliases.py` is the `AliasManager` behind resolution tier 3 — alias lookups fold case through `u_lower`, since SQLite's own `LOWER` is ASCII-only and would miss every non-English alias. `resolve.py` cascades entity resolution in 5 tiers: exact match (label + entity_type) → cross-type label match (same atom type, e.g. `tool` and `concept` both map to `concept` atom — prevents GLiNER multi-label duplicates) → alias lookup → fuzzy (RapidFuzz) → embedding similarity → create new. Creation goes through `AtomSpace.add_atom` with the probe vector handed over (`embedding=`), so the row carries the intrinsic valence pair and starts at `INITIAL_CONFIDENCE` for its kind scaled by source trust; an encoder failure logs and stores the atom without a vector (`require_vector=False`) rather than abort the extraction. Re-mention evidence rows carry `source` and a `text` of "mentioned again". `temporal.py` resolves relative dates at ingest, before embedding: GLiNER2 tags spans zero-shot with the `date`/`time` labels in `TEMPORAL_LABELS` (deliberately a separate pass from the entity labels — an entity pass emitting these would mint a concept atom called "mañana"), dateparser resolves each `date` span against the write time, and the resolution is appended (`mañana [resolved: 2026-08-27]`) rather than substituted. Both tiers must agree; a `time` span is never annotated, which is what separates "por la mañana" (in the morning) from "mañana" (tomorrow) and stops a bare hour being read as a day of the month. Idempotent — detection runs against the text stripped of any annotations it already carries. `Smrti(temporal=True)` turns it on; the facade defaults to off and every server mode passes `SMRTI_TEMPORAL` (default 1). `temporal.resolve` returns the annotated text and the resolutions, and the facade files the resolutions in the atom's `metadata.$.temporal` as it writes. The idioms no parser reaches ride the extraction LLM instead: the prompt carries a `[Write time]` header, the response carries a `temporal` array, and `_store_temporal` merges it into the same `metadata.$.temporal` — never into the text, which was embedded when it was stored, and never over a span the write-time tier already resolved, which is deterministic where the model is not. One list, one reading per span; recall renders it (`temporal` in the MCP/REST response, `[dates: …]` in the proxy's injected line). `sentiment.py` estimates valence via cosine similarity against positive/negative anchor embeddings — language-agnostic, used by all server modes as a fallback when callers don't provide explicit valence. `ner.py` — zero-shot NER via GLiNER2 on **ONNX Runtime** (default model `lmo3/gliner2-multi-v1-onnx`, the ONNX export of the multilingual model); no PyTorch anywhere, which is what lets the engine run on CPUs without AVX/SSE4.1 — torch executes `pinsrq` inside oneDNN on import, and SIGILL is a signal Python cannot catch; lazy-loaded thread-safe singleton; configurable via `SMRTI_NER_MODEL`; long texts are split into byte-sized chunks at sentence boundaries via chonkie-core (with a plain fallback splitter) to avoid GLiNER context-window truncation. 16 NER labels (note: `tool` was removed — `technology` covers software tools); when the same text span matches multiple labels, the most specific type wins (priority: person > organization > project > role > technology > skill > preference > constraint > location > event > topic > media > health > concept > goal > pronoun). Verb-phrase spans misidentified as preference/constraint entities (e.g. "Avoid at all costs") are filtered by asking the span head to tag the span as `noun_phrase` or `verb_phrase` and taking the higher score — the classifier head answers `noun_phrase` for both on this model, while the span head separates them cleanly (verb 0.86 / noun 0.45 against verb 0.03 / noun 0.58). `pronouns.py` — detects pronoun-typed entities returned by NER and merges them into named-entity atoms: first tries the alias table (`resolve_pronouns_via_aliases`), then `NERProvider.classify_pronoun`, which is a closed-class lexicon rather than a model call — asked to choose between `proper_name` and `pronoun` both the ONNX and the PyTorch builds answer `proper_name` for "she", "he", "they" and "my" alike, so that branch had never once fired; also handles retroactive batch merging at extraction time. `extract.py` — hybrid GLiNER-first extraction pipeline; called by all server modes when `SMRTI_EXTRACT=1`. Claims may carry `supersedes` (the object they replace): `_link_claims` then finds the older edge with the same subject and predicate, marks it `$.superseded_by`, draws a `contradicts` edge from the new claim edge to it naming it the loser in `$.loser`, and files negative evidence (`SUPERSEDED_PROBABILITY`, `text` saying what replaced what) against it — and does the same for the old object atom when it is a belief, so a superseded preference or constraint reads as a `known_antipattern` at recall. That is the producer the epoch's contradiction step was missing and the one path by which a belief's probability falls; before it, every evidence row the engine wrote carried 0.9 or the atom's own probability, and "disproven" was a state nothing could reach. A negative claim lowers its object's tone in both valence pairs (`_lower_tone`) — an estimate, never `VALENCE_STATED`, but the better estimate — and the gravest claim's tone is carried back to the source episode the same way. All server modes use `extract_and_link_serialized()` which acquires a per-`(tenant_id, write_space)` asyncio lock so extractions within the same session run sequentially — this ensures episode N's entities are committed before episode N+1's `_build_entity_context()` query, preventing graph fragmentation from race conditions. Cross-session concurrency is preserved. Three modes via `SMRTI_EXTRACT_MODE`: `hybrid` (default) runs GLiNER NER locally and only calls the LLM for claim extraction when ≥2 entities are found (reduces LLM calls ~40–60%); `llm` restores the original LLM-only behaviour; `local` skips the LLM entirely. `_effective_mode()` downgrades `hybrid` and `llm` to `local` (warning once) when no extraction endpoint resolves — `SMRTI_EXTRACT_URL` falls back to `SMRTI_UPSTREAM_URL` and then to nothing, since `serve rest` and `serve mcp` have no upstream and a public default would post episodes to an endpoint the operator never chose. The proxy passes its own effective `_UPSTREAM` so its extraction keeps following whatever it forwards to. In hybrid mode the claims-only LLM call may also emit new entities of type `role`, `technology`, `skill`, `topic`, `media`, `health`, `concept`, `preference`, or `constraint`; preference/constraint reclassify concept atoms to belief in-place, while the rest are created as new concept atoms with a `mentions` edge to the episode. `_link_claims` auto-creates missing claim object atoms as concepts via the entity resolver rather than silently dropping claims with unknown targets. Before each LLM extraction call, `_build_entity_context()` queries the top salient concept, belief, and goal atoms (person, organization, project, role, tool, technology, skill, location, event, topic, media, health, goal, preference, constraint) from the memory graph and injects them as a `[Known entities]` block so the LLM can resolve pronouns ("I" → person, "we" → organization) even when the name isn't in the current message — using persisted memory, not raw conversation history. Each entity carries up to six of the facts already recorded about it (`Alice (person): lives_in Amsterdam; works_for Acme`), superseded ones excluded, which is what lets the model say that a new fact replaces an old one. `prompts.py` holds every extraction prompt and `ENTITY_TYPES`, the 16 types the LLM may emit — a different list from the 16 NER labels: it keeps `tool` (which `resolve.py` tier 2 folds into the same `concept` atom as `technology`) and has no `pronoun`, since only NER tags those. `extract.py` validates LLM output against `ENTITY_TYPES`, and switches to `AGENT_EXTRACTION_PROMPT` for agent-authored turns so a model's own reply is mined for self-knowledge rather than read as user testimony. The extraction prompt includes a formal JSON schema and eight few-shot examples (tool migration, org/location, error/failure with negative valence, coreference with known entities, goal/preference/constraint, hobbies/pets/fears, health/skill/media/topic, role/focus-area). `max_tokens=4096` gives thinking models (Qwen3, DeepSeek-R1) enough budget to finish their chain-of-thought and still emit the JSON response; `reasoning_content` is used as a fallback when `content` is empty. Thinking mode is controlled by `SMRTI_EXTRACT_THINKING` (`auto` / `disabled` / `enabled`; default `disabled` — extraction works better with thinking off): `disabled` injects `chat_template_kwargs={"enable_thinking":false}` (llama.cpp / vLLM Qwen3 style). Extraction request timeout is controlled by `SMRTI_EXTRACT_TIMEOUT` (seconds, default 60; lower for fast-fail on slow local models). Entity lookup is case-insensitive with `setdefault` collision safety so subject/object casing mismatches never silently drop relation edges.

**Spaces (`spaces/`):** `set_ops.py` implements five set-theory operations on memory spaces — `space_overlap`, `space_intersection`, `space_difference`, `space_union`, `space_symmetric_difference` — all using a **contextual similarity** score that blends three signals: embedding cosine similarity (w=0.6), entity-type compatibility (w=0.2), and graph-neighborhood similarity (w=0.2). The neighborhood signal disambiguates homonyms: two atoms both labelled "Java" will diverge because one's neighbors are "Indonesia/Bali" and the other's are "JVM/Spring". All three signals are language-agnostic. `emergence.py` materialises a **bridge space** from a `SpaceOverlap` result when Jaccard ≥ `min_jaccard` (default 0.1): each matched pair becomes a bridge atom with PLN-merged truth values, averaged STI, max LTI, and intensity-weighted blended valence; `bridge` relation edges connect the new atom back to both source atoms. Bridge spaces are named `{sorted_a}_x_{sorted_b}` so the operation is commutative. Existing bridge atoms are updated in-place (identified by `bridge_source_a`/`bridge_source_b` metadata) to avoid duplication. A space is never bridged to itself (A∩A is all of A, so the bridge would duplicate the whole space). Bridging happens only when a caller asks for it (`materialize_bridge`, the `space_merge` tool and route); the epoch used to compare every space against every other every tenth pass — `O(500²)` cosines per pair in pure Python, on a timer, writing atoms into spaces nobody asked for — and no longer does. The five set operations and `materialize_bridge`/`list_spaces` are also exposed on the `Smrti` facade and as MCP tools (`smrti_space_overlap`, `smrti_space_intersection`, `smrti_space_diff`, `smrti_space_merge`, `smrti_list_spaces`).

**Personality (`personality/`):** `PersonalityProfile` dataclass with 17 hyperparameters. Six presets (`balanced`, `analytical`, `curious`, `empathetic`, `maverick`, `deterministic`) defined as `PersonalityProfile` instances in `params.py` (re-exported by `presets.py`) and loaded into the `personality` DB table per tenant/space pair. `deterministic` is optimized for agentic workflows: fast learning (lr=0.4) + slow decay (0.005), high LTI promotion threshold (0.85), laser-focus attention (boost=0.8, propagation=0.05), and similarity-gated confidence ranking.

**Servers (`servers/`):** `config.py` centralises the shared env-var defaults (`SMRTI_DB`, `SMRTI_PERSONALITY`, `SMRTI_TENANT_ID`, `SMRTI_SPACE`, `SMRTI_READ_SPACES`, `SMRTI_EXTRACT`, `SMRTI_EXTRACT_MODE`, `SMRTI_EXTRACT_URL`, `SMRTI_EXTRACT_MODEL`, `SMRTI_EXTRACT_THINKING`, `SMRTI_TEMPORAL`, `SMRTI_IGNORE_PATTERNS`, `SMRTI_API_KEY`, `SMRTI_CORS_ORIGINS`, `SMRTI_VIZ_DBS`, `SMRTI_INJECT_MAX_CHARS`, `SMRTI_UPSTREAM_URL`) read by all server modes. When `SMRTI_API_KEY` is set, every REST/proxy/viz request must send `Authorization: Bearer <key>` or `X-Api-Key: <key>`; auth is off by default for local use. `SMRTI_VIZ_DBS` (`os.pathsep`-separated) is the allowlist for the visualizer's `?db=` param: `_db_mem` opens a path only when it is already in the shared `Database` registry (the DB the server was started with) or named in that list, and 404s an allowlisted path that does not exist rather than materializing an empty DB — the endpoints are unauthenticated unless `SMRTI_API_KEY` is set, so an ungated `?db=` would let a GET open or create any file as a SQLite database. Four more are read at their point of use rather than through `config.py`: `SMRTI_EXTRACT_TIMEOUT` by `extraction/extract.py`, `SMRTI_NER_MODEL` by `extraction/ner.py`, `SMRTI_RECALL_TOP_K` and `SMRTI_RECALL_MIN_CONFIDENCE` by `proxy.py`, `SMRTI_REFLECT_INTERVAL` by `reflect_loop.py`, and `SMRTI_RUN_DIR` by `cli.py` (the PID directory `smrti serve` writes and `smrti stop` reads). `mcp.py` wraps Smrti as MCP stdio tools; `handle_tool()` recall response includes `severity` and `intensity` fields. All three modes (MCP, REST, proxy) auto-estimate valence via `extraction/sentiment.py` when callers don't supply an explicit value, activating the error-avoidance memory path for negative content. All three modes call `extraction/extract.py` (via `extract_and_link_serialized`) after every `remember` operation to extract entities/claims and build concept nodes + relation edges (enabled by default via `SMRTI_EXTRACT`; proxy uses request auth, proxy and REST forward the request `Authorization` header; MCP passes no auth — works as-is with local LLMs). The proxy's `_store_exchange` awaits user extraction before assistant extraction sequentially so the user's entities are visible when extracting the assistant's response. `rest.py` is a FastAPI REST server; besides the memory routes it exposes the two-space operations as `POST /space_query` (`op` = overlap/intersection/diff) and `POST /space_merge`, thin wrappers over the same `handle_tool` handlers the MCP tools use. Both resolve their instance through `_other_space_mem`, which 400s a self-compare: against itself overlap is a trivial 1.0 bought with a 500-atom scan and an embedding pass per atom, and a merge would materialize an `x_x_x` bridge of every atom paired with itself in a space nothing else writes. `viz_routes.py` is the shared visualizer router (graph explorer, atom CRUD, LLM call log endpoints, and a zero-dependency Prometheus `GET /metrics` text exposition — atom counts, epoch count, and active personality hyperparameters labeled by tenant/space) mounted by both REST and proxy. Its read-only endpoints run every query through the server's configured `(SMRTI_TENANT_ID, SMRTI_SPACE)` handle and pass the requested tenant/space as SQL parameters, rather than asking `get_mem` for an instance per requested pair — on the proxy each distinct pair mints a `Smrti` and writes a personality row, so browsing the graph would create rows for tenants that do not exist, and `/status` / `/metrics` would report a hardcoded `default` instead of the configured tenant. `proxy.py` is an OpenAI-compatible proxy with content-based episode deduplication (skips storing identical episodes for the same tenant/space) and severity-aware memory injection: recalled memories are split into two sections — behavioral constraints (`YOU MUST NOT`, `AVOID` for `critical_warning`/`known_antipattern`) and background context (`Note:` for `context`), each with its own preamble — and contextual query reformulation (configurable via `SMRTI_QUERY_MODE`, `SMRTI_QUERY_CONTEXT_MSGS`, `SMRTI_QUERY_MAX_CHARS`). All severity levels include a `confidence` qualifier. `call_log.py` is a shared in-process ring buffer (200 entries) that captures every LLM call across all serve modes — full request/response, timing, status, error, and tenant_id; both REST and proxy expose `GET /llm-calls` and `DELETE /llm-calls` endpoints, and the visualizer shows them in an "LLM Calls" debug tab. `reflect_loop.py` runs periodic background consolidation across all server modes (interval controlled by `SMRTI_REFLECT_INTERVAL`, default 60s, 0 to disable), for the instances that were used since their last epoch: `Smrti.ops_since_reflect` counts remember/believe/recall/reinforce/forget calls and `reflect()` resets it, so an epoch is a unit of the agent's activity and an idle space — served or not, or evicted from the proxy's instance LRU — does not age. Run on the timer alone, a memory lost 98% of its attention in an hour of server uptime and nothing while the server was down. `SMRTI_RECALL_MIN_CONFIDENCE` left unset means the personality's `min_confidence_to_surface`; the proxy's `_enrich_content` leaves superseded claims out of an entity's description. `POST /reinforce` (atom ids plus an optional weight) reports that memories were used; it is a REST route and a `handle_tool` handler, not an advertised MCP tool. `tools.py` defines the 8 advertised MCP tool schemas, each named with a `smrti_` prefix (`smrti_remember`, `smrti_recall`, `smrti_reflect`, `smrti_forget`, `smrti_status`, `smrti_personality`, `smrti_space_query`, `smrti_space_merge`). `believe`, `space_overlap`, `space_intersection`, `space_diff`, and `list_spaces` are retained as legacy handlers in `handle_tool()` for REST backward-compatibility and direct callers, but are not advertised to MCP clients. `remember` subsumes `believe` (use `type=belief` + `evidence`); `status` includes the spaces list; `space_query` covers overlap/intersection/diff via an `op` parameter.

## smrti-town

City-builder simulation built on the Smrti memory engine: the player founds a town (places the Town Hall, picks a mayor, gets a 4-advisor council), then citizens with private Smrti memory graphs immigrate, work, and petition while an LLM council debates what to build. Lives in `src/smrti_town/` alongside `src/smrti/` and ships in the same wheel, so `pip install smrti` installs the simulation and its frontend.

```bash
# Start the town simulation server (port 8430)
smrti serve town

# Or directly
python -m uvicorn smrti_town.server:app --port 8430
```

`src/smrti_town/README.md` is the canonical description of how the town behaves — env vars, tick phases, REST routes, WebSocket messages. What follows is the code-level map that file does not carry; when the two disagree, the README is the one to fix.

**Game flow:** an opening phase followed by the gameplay tick loop, both owned by `server.py` module-level `_game` state guarded by an asyncio lock. Opening endpoints must be called in order: `POST /opening/place-hall` (grid coords) → `POST /opening/choose-mayor` (index into LLM-generated candidates; builds the council + citizen specs, falls back to `scenarios/fallback.py::create_fallback_council()` — 5 hardcoded members — when the LLM is unreachable) → `POST /opening/begin` (creates `Citizen` objects, starts `_tick_loop`). Each endpoint 400s if called in the wrong phase.

**Tick loop (`server.py::_tick_loop`), phases per tick:** `Director.compute_delta` picks the tick's sim-time delta and advances the calendar → the crime rate (`EventManager.crime_rate`) → perceive + decide (rule-based, no LLM) → needs tick using the just-decided action → the dead are buried (`_bury`) → every `MEMORY_REFLECT_INTERVAL_TICKS` ticks: memory consolidation, `update_relationships` in an executor, a culture pass every `CULTURE_INTERVAL_TICKS` (not awaited), and `_save_game` → action resolution (`_resolve_actions`: need satisfaction, economic effects, skill practice, the episode each citizen remembers it by) → events (`_roll_events`) → economy tick → milestone check (`Chronos`) → game-over check → dialogue queue submissions (capped per tick) → once a sim-day (`PETITION_CHECK_INTERVAL_HOURS`): `_fill_open_jobs` and petitions → council meeting check (`COUNCIL_MEETING_INTERVAL_HOURS` = 24 sim-hours) → every `IMMIGRATION_CHECK_INTERVAL_HOURS`: births (`check_births` → `_born`), departures (`check_departure` → `_depart`), immigration → the tick's experiences, accumulated all tick long, written in one executor batch (`_write_experiences`). Results are broadcast to WebSocket `/ws` clients (`tick`, `state`, `phase`, `council_meeting`, `council_result`, `council_counter`, `petition_update`, `building_placed`, `immigration`, `event`, `game_over`, `dialogue_patch`, `paused`, `resumed`, `reset`, `pong`).

**LLM integration (`llm.py`):** `LLMSettings` (dataclass, serialisable) + `LLMClient` (async httpx wrapper) with per-call template fallbacks. `generate_mayor_candidates()` (opening), `generate_council_meeting()` (advisor debate + proposal, constrained to `BUILDING_CATALOG` keys filtered by population/built prerequisites), `generate_immigrants()` (newcomer families per housing type; `PopulationManager.generate_fallback_family()` when it fails), `generate_dialogue()` / `generate_dialogue_batch()` (in-character citizen dialogue, queued via `DialogueQueue` and patched into the frontend via `dialogue_patch`). All LLM-supplied values are validated and clamped (traits, personalities, skills). Default endpoint `http://0.0.0.0:8421/v1` (the `smrti serve proxy` address), model `Qwen3.5-9B-Q8_0.gguf`; `SMRTI_TOWN_LLM_URL` and `SMRTI_TOWN_LLM_MODEL` override both at startup (read when `LLMSettings` is built, so before the server module is imported), and `GET/POST /settings` changes them at runtime. `POST /regenerate` resets the game to the opening phase and broadcasts `{"type":"reset"}`.

**Modules:**

- `server.py` — FastAPI app owning all game state and the tick loop. REST: opening endpoints (above), `POST /council/approve|reject|counter`, `GET /petitions` + `POST /petitions/{idx}/approve|dismiss`, `POST /place-building`, `GET /state`, `GET /agents`, `GET /agents/{name}/memories`, `GET /economy`, `GET /culture` (Space_Culture atoms), `GET|POST /settings`, `POST /start|pause|resume|skip|regenerate`, static frontend from `static/`.
- `agent.py` — `Citizen`: needs + traits + `Smrti` instance. Rule-based `decide()` — no LLM calls; place and person choices are weighted by the *mood* of recalled memories that name the place or person (`_memory_mood`: `r.atom.valence.valence`, the pair propagation moves, read without the access boost). This is the consumer of the engine's valence propagation and `mood_inertia`. Writes episodes to `Agent_Space_{name}`; reads own space + `World_Space` + `Space_Culture`. `experience(text, valence)` is the write half of that loop: action resolution calls it once per resolved action with a stated tone from `EXPERIENCE_VALENCE` — a meal, a purchase, work, study, leisure, treatment, a conversation — and `talk_tone` decides whether a conversation was a quarrel (`QUARREL_PROBABILITY` plus `QUARREL_STUBBORNNESS_WEIGHT` × the pair's mean stubbornness); both parties remember it, naming the other and the place. Until it existed the only writes into a citizen's space were the bio and role at creation, so every place carried the same mood and the README's "avoids the tavern after an argument" had no producer. Food and social-venue choice go through `_nearest_liked` — distance less three times the place's mood, every venue kind competing — where the earlier by-type chain tried taverns first whatever the memories said, and food went to the nearest place regardless. Experiences are written agent-authored (`metadata.source = agent`): the simulation reported them, and the engine decays and prunes such episodes once forgotten, which is what bounds a graph fed every tick; a quarrel is `-0.8`, under the `-0.7` line past which the engine gives a memory a long-term floor, so quarrels outlive the meals around them. `memories_about(name, top_k, boost)` is the one reader, and `_memory_mood` reinforces the atoms it decided on (`Smrti.reinforce`, capped per epoch by the engine). `perceive` recalls nothing: it used to run a recall per citizen per tick into a `memories` field nothing read. `personality_params` reads the citizen's personality row (the genome), `inherit` runs the graph on a blended one, `from_dict` reopens a saved citizen. The tick loop consolidates every citizen's graph every `MEMORY_REFLECT_INTERVAL_TICKS` ticks (skipping graphs that saw nothing), so memories age and settle in the demo.
- `drives.py` — `CitizenNeeds`: 9-level Maslow hierarchy (hunger, shelter, health, safety, social, education, purpose, culture, actualization); lower needs dominate.
- `economy.py` — `EconomyManager`: treasury, per-citizen wallets, taxation, commerce, building costs/maintenance from `BUILDING_CATALOG` (defined in `config.py`).
- `council.py` — governance: meetings, proposals, debates; mayor personality biases decisions.
- `petition.py` — `PetitionManager`: needs-based citizen petitions with signing/merging; surfaced to the player for approve/dismiss. The tick drafts them once a sim-day (`PETITION_CHECK_INTERVAL_HOURS`): `check_citizen_needs`, then `_business_petitions` for every adult `economy.check_entrepreneurship` passes (a petition for the first commercial building the town can host), then `merge_similar`; `_fill_open_jobs` runs on the same cadence. Approving a petition with a building broadcasts `council_result` with `awaiting_placement`, the way a council approval does, and `place_building` then makes the petitioner the owner: a stake of `ENTREPRENEURSHIP_SAVINGS_THRESHOLD` into the treasury, the workplace, and an episode. The tick payload carries `petitions` in the panel's shape (`_petitions_payload`; list position is the route index, status `pending` for active) and the council meeting's town state carries the active ones.
- `population.py` — `PopulationManager`: pull factors (housing, jobs, services, reputation) → immigration; fallback newcomer generation.
- `gridmap.py` — `GridMap`: isometric grid for building placement. `navgrid.py` — `NavGrid`: walkability + A* pathfinding. `spatial.py` — `TownTopology` + `Place` adjacency graph.
- `skills.py` — `SkillSet`: 8 skill categories with learning and role-checking (profession activation).
- `calendar.py` — `SimCalendar`: hour/day/season/year. `director.py` — `Director` adaptive tick pacing (scene 0.25h when ≥2 citizens share a place, routine 2h, montage 8h, skip 168h) + `Chronos` milestones.
- `dialogue_queue.py` — `DialogueQueue`: bounded async queue capping concurrent in-flight LLM dialogue requests.
- `worldgen.py` — opening-sequence orchestrator: seeds `World_Space` (topology + council facts) and `Space_Culture` (founding values), creates per-citizen Smrti instances.
- `lifecycle.py` — `update_relationships` moves every acquainted pair up or down the tiers from the graph: `check_relationship_progression` takes the lower of the two moods the pair hold of each other, the LTI the epoch has given their memories of each other (read with the access boost, so a pair a citizen keeps thinking about is what gets promoted), how many such memories each holds, and the years since the tier was reached; `check_relationship_regression` takes quarrels in excess of good times. Both directions are set together and `relationship_since` stamped. `check_births` asks `PopulationManager.check_natural_growth` for eligible couples, then requires the gate's years together, a shared home with room, and `BIRTH_PROBABILITY`; `create_child` blends the parents' `personality_params` (read off each citizen's personality row) and the server's `_born` runs the child's graph on them through `Citizen.inherit` → `set_personality_profile`. `satisfaction` feeds `check_departure`. Deaths stay in `Citizen.tick_state`; the tick's `_bury` frees home, work and wallet and writes the death to everyone closer than an acquaintance, `_depart` does the same and drops the citizen from the list (the memory graph stays in the file). Relationships run on the consolidation cadence, births and departures on the immigration cadence.
- `events.py` — `EventManager.roll_sporadic` / `roll_crisis` as before, plus `apply_effects` (treasury, needs as fractions where `health`/`safety`/`social` name the good quantity and `hunger` the deprivation, wallets, and the episode every affected citizen remembers it by at `EVENT_VALENCE`) and `crime_rate` (idle adults, plus an active crime wave, halved by a constabulary — what the safety need now reads). The tick's `_roll_events` rolls once per routine tick's worth of sim time so pacing does not change how eventful a day is, gives a crisis `CRISIS_DURATION_HOURS`, and demolishes what a fire took through `_demolish`.
- `culture.py` — `run_culture_pass`: `materialize_bridge` between every pair sharing a place (Jaccard ≥ 0.3), then promotion of every bridge atom at confidence ≥ 0.5 into `Space_Culture` once per distinct text, carrying the tone it was written with. Runs every `CULTURE_INTERVAL_TICKS` in an executor and is not awaited: a bridge is seconds of pure-Python cosines. An earlier version called the facade with a `tenant_id` argument it does not take and read atom fields off the result object, all swallowed by broad excepts, so it had never run.
- `persistence.py` — `snapshot`/`save`/`load`/`clear`/`restore`: one JSON row per tenant in a `town_state` table of the town's own database. Every state class serializes itself (`from_dict` on `TownTopology`, `GridMap`, `Director`, `Chronos`, `Citizen` were added for this; homes and workplaces are reassigned from what each citizen recorded). The server saves at every consolidation, at `opening_begin` and on shutdown, resumes in `_lifespan` startup when a row exists, and `regenerate` clears it.

**Frontend sprites:** `static/sprites.json` was regenerated from the sheet's alpha bounds inside hand-named regions — the old file had the right rectangles under the wrong names (the frames called `stone_1..3` sat on the water tiles, `cottage_1..3` on a store, a shop and a bank, `park` spanned two buildings). Building frames are `sprite_key` from the server plus the rolled `sprite_variant` (`cottage_1` + variant 2 → `cottage_3`), resolved by `BuildingRenderer._frameFor`; before that the numeric variant was used as the frame name and every varied building drew as the town hall. `manor` has three variants and `farm` two.

**Space hierarchy:** `World_Space` (topology + council facts, seeded at founding) → `Agent_Space_{name}` (private per-citizen) → `Space_Culture` (founding values plus what `culture.py` promotes; read by every citizen, served by `GET /culture`). Bridge spaces (`{a}_x_{b}`) hold what two citizens remember alike. `Place.space_name` (`Place_Space_{name}`) exists in the code and nothing reads one.

**Key design decision:** Personality hyperparameters are inherited biologically — child gets a blend of both parents' personality params with stress-boosted Gaussian mutation, bounded by `PARAM_BOUNDS` in `config.py` (`lifecycle.py::create_child`, applied to the newborn's graph by `Citizen.inherit`).

## Benchmarking

`bench/` is not part of the wheel. Neither dataset ships with the repo, so `bench/fetch.py` (`make datasets`) downloads both into `data/` using the stdlib alone; the Makefile defaults to paths nothing else creates, and before the fetcher existed the documented command failed on a fresh clone with no way to fix it. Two harnesses share `bench/harness.py` (config fingerprint, baseline gate, CLI) and `bench/answering.py` (answer, judge, and a concurrent `score_batch` — sequential grading turned a 500-question run into an hour of waiting on an idle endpoint). `bench/halumem` grades three ways — correct, hallucination, omission — because a system that invents an answer and one that admits it has no record are not the same failure, and it gates on the hallucination rate *rising*; only its question-answering task is implemented, not memory extraction or updating. `--extract-url`/`--extract-model` turn on the entity graph, which the harnesses could not do at all before — the facade they ingest through never extracts, only the server modes do, so the `extraction` config key described a state rather than controlling one. It costs 1.25s and one LLM call per turn against 18ms without, and its effect on the two benchmarks here is unmeasured. `--epochs N` runs N `reflect()` passes over each history before it is queried and `--top-k` overrides the locked budget; both enter the config fingerprint only when set (`apply_run_modes`), so the default run still gates against the recorded baseline and a run under either mode is reported on its own. Without `--epochs` the harness measures a store where every atom has zero attention and a constant confidence, which is a measurement of the retrieval half alone. The recorded baselines predate the ranking change that scales standing by relevance. `bench/longmemeval/adapter.py` ingests each LongMemEval-S question's history into its own space (one space per question — another question's haystack is not this one's distractor set), preserving the session dates on `created_at` and storing assistant turns as agent-authored, then scores `recall` on retrieval hit rate, evidence recall, and session hit rate. Gold evidence is matched by atom id, never by text. The question subset is deterministic but not the front of the file — the dataset is grouped by question type, so `load_questions` takes one question per type in turn, and a 40-question slice covers all six abilities instead of forty single-session-user questions. `run.py` compares the run against `baseline.json` and exits non-zero when the hit rate drops past the config's tolerance; a baseline recorded under a different `config_hash` is refused rather than compared. `answering.py` is the optional end-to-end half and gates nothing — it needs a judge model, and folding answer accuracy into the gate would let a good answering model hide a retrieval regression.

## Rules

- **No hardcoded English.** Smrti is multilingual (50+ languages). Never use English word lists, prefixes, or patterns for filtering or logic. Use language-agnostic approaches: GLiNER `classify_text`, embedding similarity, span-length ratios, or word-count heuristics.

## Key Design Decisions

- **Append-only evidence log:** Truth values are primarily updated through the evidence log, revised during epochs by the count-based PLN rule in `truth.py`. Each row records the observation (`text`) and who made it (`source`). Direct truth mutations occur only for policy operations: contradiction resolution (a named loser is cut to `SUPERSEDED_PROBABILITY` and loses confidence; an unnamed contradiction weakens the less confident side), forget (sink below the surfacing floor), and reinforcement (a client reporting that a memory was used)
- **Forgetting is final:** `forget()` retrieves without the access boost, sinks confidence below the surfacing floor, stamps `$.forgotten`, and the stamp excludes the atom from every recall, from every lift (the permanence heal, reinforcement), and from the LTI floors — so the pruner may remove it, user testimony or not
- **Epochs are units of use:** the reflect loop consolidates a space once per interval in which it was used and never otherwise. Decay rates are per epoch, so they are per active interval, not per minute of uptime
- **Multi-tenant isolation:** Every query is partitioned by `tenant_id` and `space`. Two invariants back this, and `tests/test_tenancy_isolation.py` pins both down: (1) *tenant walls* — no read, write, epoch, set operation, or entity resolution may observe or modify another tenant's rows; (2) *overlay reads are read-only* — a space reads its whole overlay but only ever mutates its own write space, so `fan_out` boosts STI in `write_space` only, `EntityResolver` reinforces and files evidence only for atoms that live in `write_space`, and `run_epoch` scopes evidence application and contradiction resolution to atoms in the space being consolidated. Deletes cascade the other way: `clear_space` and the epoch pruner remove tenant-wide relation edges (bridge spaces point back into both parents, and `source_id`/`target_id`/`evidence.atom_id`/`aliases.atom_id` are enforced foreign keys) before removing the atoms themselves
- **Lazy embedding init:** FastEmbed model loads on first use, not at import time
- **Salience over recency:** Retrieval ranks by a weighted salience score, not timestamps
- **Error-avoidance memory:** Severe negative-valence atoms (valence < -0.7, intensity > 0.7) get an LTI floor of 0.5 on creation, preventing epoch pruning. Salience weights shift dynamically for negative-valence atoms (valence < -0.5). Recall results carry a `severity` classification (`critical_warning` when the caller stated the valence on a non-`concept` atom whose own valence < -0.5 and own intensity > 0.5, `known_antipattern` at probability < 0.3 and confidence > 0.3, otherwise `context`) used by all serving modes. Every valence read for these judgements is the atom's own, not the mood propagation gave it.
- **Testimony outlives inference:** confidence gates surfacing the way LTI gates pruning — an atom below `min_confidence_to_surface` can never be recalled, so it can never be restated, so no new evidence lifts it back. User-stated episodes and beliefs therefore decay only to that floor, and a belief asserted at `PERMANENT_PROBABILITY` (0.95) is exempt from confidence decay entirely. Both floors only hold an atom already at or above them: `forget()` sinks memories on purpose, and a floor that reached down would undo it one epoch later. Concepts, goals, and everything agent-authored keep decaying freely. The floor is applied at recall by default (`recall(min_confidence=None)`), so the preset's promise is kept for a caller who did not repeat the number.
- **Relevance gates standing:** salience is `similarity × (w_sim + standing)`. Standing — attention, confidence, LTI, valence — decides the order among atoms that are about the question and cannot lift one that is not. Nothing is injected into the candidate set that the query or an edge out of a hit did not reach.
